## Summary

Kubernetes Pod Certificates ([KEP-4317](https://github.com/kubernetes/enhancements/issues/4317)) let a pod ask for an X.509 certificate through a `podCertificate` projected volume. The kubelet generates the key on the node, creates a `PodCertificateRequest` (PCR) naming a signer, and mounts the issued certificate chain and key into the pod, rotating them before they expire. `PodCertificateRequest` is GA in `certificates.k8s.io/v1` in Kubernetes 1.37. Since 1.36 it carries a stub PKCS#10 request (`spec.stubPKCS10Request`) that proves possession of the key.

The platform provides the request, delivery and rotation, but not the signer. This design makes cert-manager a PCR signer, backed by existing Issuers and ClusterIssuers, using the same signer names as the experimental `CertificateSigningRequest` controllers. Workloads then get short-lived, automatically rotated certificates that carry their verified Kubernetes identity, with no sidecar and no CSI driver.

## Motivation

Pod identity certificates are a common need: mTLS between services, SPIFFE identities, client certificates for databases. Today cert-manager users need [csi-driver](https://cert-manager.io/docs/usage/csi-driver/) or [csi-driver-spiffe](https://cert-manager.io/docs/usage/csi-driver-spiffe/) for this, or they mount a Secret from a `Certificate`, which every pod with access to the Secret shares. With Pod Certificates, the key never leaves the node, the certificate is bound to one pod, and the kubelet handles rotation.

[#8378](https://github.com/cert-manager/cert-manager/issues/8378) asks for this. As discussed there, the `ExperimentalCertificateSigningRequestControllers` don't cover it: a `CertificateSigningRequest` is created by whoever holds the key, so it can't give a certificate that another pod can't impersonate. A PCR is created by the kubelet for one pod, and kube-apiserver checks that the pod, service account and node match.

### Goals

- Sign PCRs whose `spec.signerName` names a cert-manager Issuer or ClusterIssuer, using the signer-name format of the CSR controllers.
- Derive the certificate's identity only from fields kube-apiserver verifies (namespace, service account, pod), never from the pod-author-controlled stub request or `unverifiedUserAnnotations`.
- Require an explicit opt-in on each Issuer or ClusterIssuer, so that a pod can't get certificates from a CA its administrator didn't intend for pod identities.
- Respect `spec.maxExpirationSeconds` and set `status.beginRefreshAt` so the kubelet rotates in time.
- Ship behind an alpha feature gate, off by default.

### Non-Goals

- ACME issuers. Public CAs don't issue certificates for in-cluster identities; such requests are denied.
- Replacing csi-driver or csi-driver-spiffe. They keep working, including on clusters older than 1.37.
- Approver-policy integration in alpha (see Open questions in [Graduation Criteria](#graduation-criteria)).
- Trust bundle distribution. Workloads still get the CA bundle from trust-manager or a `ClusterTrustBundle`.

## Proposal

A new controller, enabled by `ExperimentalPodCertificateRequestControllers`, watches `PodCertificateRequest` objects. For each request whose signer name refers to an opted-in issuer of a supported type, it builds a certificate for the requesting pod's identity, signs it with that issuer, and writes `status.certificateChain`, `notBefore`, `notAfter`, `beginRefreshAt` and an `Issued` condition. Requests it can't serve get a `Denied` or `Failed` condition with a reason.

### User Stories

#### Story 1: SPIFFE mTLS without a CSI driver

A platform team runs a CA Issuer `mesh-ca` in namespace `payments`, and opts it in to pod certificates. A payments pod declares:

```yaml
volumes:
- name: identity
  projected:
    sources:
    - podCertificate:
        signerName: issuers.cert-manager.io/payments.mesh-ca
        keyType: ECDSAP256
        credentialBundlePath: credentials.pem
```

The pod gets a certificate with the URI SAN `spiffe://cluster.local/ns/payments/sa/payments-api`, valid for at most 24 hours, which the kubelet rotates automatically.

#### Story 2: Cluster-wide workload identity

A cluster administrator opts a `ClusterIssuer` backed by an internal CA in to pod certificates. Any pod in the cluster can then request a certificate for its own service account identity with `signerName: clusterissuers.cert-manager.io/workload-ca`.

### Notes/Constraints/Caveats

- kube-apiserver verifies the stub request's signature (proof of possession) and that the pod, service account and node fields match the pod. The signer doesn't need to repeat those checks, but it must not trust the stub request's subject or SANs.
- PCRs are short-lived by design (24 hours by default, `maxExpirationSeconds` between 1 hour and 91 days). The CA issuer signs locally, so this load is cheap. Remote issuers need care (see [Supported issuers](#supported-issuers)).

### Risks and Mitigations

- **Unintended use of a CA.** Without an opt-in, any pod could name any ClusterIssuer and get a certificate from it. Mitigation: issuers must carry the opt-in annotation, otherwise the request is denied with reason `IssuerNotEnabledForPodCertificates`.
- **Identity spoofing through the stub request.** Mitigation: the certificate is built from the verified spec fields only. The stub request is used for its public key only.
- **Volume.** Every pod with the volume gets a new certificate at least daily. Mitigation: alpha supports only the CA issuer, and the controller reports PCR signing metrics so load is visible.

## Design Details

### Signer names

The controller uses the existing CSR signer-name format and parser (`SignerIssuerRefFromSignerName`):

- `issuers.cert-manager.io/<namespace>.<name>`: a namespaced Issuer. The PCR must be in the same namespace, otherwise it is denied with reason `IssuerNamespaceMismatch`, so a pod can't use another namespace's Issuer.
- `clusterissuers.cert-manager.io/<name>`: a ClusterIssuer.

Requests with any other signer name are ignored, so other PCR signers can run alongside cert-manager.

### Opting an issuer in

An Issuer or ClusterIssuer serves PCRs only with the annotation:

```yaml
metadata:
  annotations:
    experimental.cert-manager.io/pod-certificates: "true"
```

An annotation keeps the alpha free of API changes. If the feature graduates, the annotation would be replaced by a field (Open Question 1).

### Certificate contents

For alpha, issued certificates carry a SPIFFE identity:

- URI SAN `spiffe://<trust-domain>/ns/<namespace>/sa/<serviceAccountName>`, where the trust domain comes from the new controller flag `--pod-certificate-trust-domain` (default `cluster.local`), matching csi-driver-spiffe's format;
- no subject, no DNS SANs;
- key usages `digital signature` (plus `key encipherment` for RSA keys), extended key usages `server auth` and `client auth`;
- the public key from `spec.stubPKCS10Request`. Requests for a key type the issuer can't sign are denied with `UnsupportedKeyType`, which tells the kubelet to retry with another key type.

The pod name and UID aren't put in the certificate, so that all replicas of a workload share an identity, as with SPIFFE. Other identity formats are Open Question 2.

### Validity and refresh

- `notBefore` is the signing time minus a small clock-skew allowance (1 minute).
- `notAfter` is `notBefore + spec.maxExpirationSeconds`, limited to the issuer certificate's own `notAfter`. kube-apiserver rejects lifetimes shorter than one hour, so if the issuer certificate expires within the hour, the request fails with reason `IssuerExpiring` rather than issuing an invalid certificate.
- `beginRefreshAt` is set at two thirds of the lifetime, matching cert-manager's default renewal point for Certificates.

### Controller flow

1. Ignore PCRs with a foreign signer name, or that already have an `Issued`, `Denied` or `Failed` condition.
2. Resolve the issuer from the signer name. If it doesn't exist yet, requeue: the issuer may be created later.
3. Deny the request if the issuer isn't opted in, its namespace doesn't match, or its type isn't supported.
4. Wait until the issuer is `Ready`.
5. Parse the stub request, take its public key, build the certificate template described above, and sign it with the issuer.
6. Update the PCR status (`certificateChain` with the leaf first, then intermediates from the issuer, plus `notBefore`, `notAfter`, `beginRefreshAt` and the `Issued` condition) and record an event. A signing error sets `Failed` with the error as message.

The controller follows the structure of `pkg/controller/certificatesigningrequests`. The issuer-specific signing reuses the CA signer that the CSR controller already uses.

### Supported issuers

- **Alpha:** `CA` issuers only. They sign locally with the issuer's key, which suits the volume and short lifetimes of pod certificates.
- **Later (Open Question 3):** `Vault` (with the role set to ignore CSR SANs and the SPIFFE ID passed as `uri_sans`), CyberArk/Venafi, and external issuers. External issuers can't be reached through `CertificateRequest`, because the CSR in a `CertificateRequest` would have to carry the pod identity and be signed by the pod's key, which the controller doesn't have.
- `SelfSigned` and `ACME` issuers are always denied (`UnsupportedIssuer`).

### RBAC

The controller's ClusterRole gains:

- `get`, `list`, `watch` on `podcertificaterequests`, and `update`/`patch` on `podcertificaterequests/status`;
- `sign` on `certificates.k8s.io` `signers` with resource names `issuers.cert-manager.io/*` and `clusterissuers.cert-manager.io/*`, as the CSR controllers already have. Whether kube-apiserver checks exactly this verb for PCR status updates is to be confirmed against the PodCertificateRequest admission code during implementation.

These rules are only rendered by the Helm chart when the feature gate is enabled, so default installs keep their current permissions.

### Test Plan

- **Unit:** signer-name handling; namespace and opt-in denials; certificate template contents (SPIFFE URI, usages, lifetime, refresh time, clipping to the issuer's expiry); `UnsupportedKeyType`; ignoring the stub request's SANs.
- **Integration (envtest, Kubernetes 1.37):** create PCRs against a CA Issuer and ClusterIssuer and assert status and conditions.
- **E2E (kind 1.37):** a pod with a `podCertificate` volume gets a certificate chaining to the CA with the expected SPIFFE ID, and a rotated one after `beginRefreshAt` (with a short `maxExpirationSeconds`).

### Graduation Criteria

- **Alpha:** behind `ExperimentalPodCertificateRequestControllers` (off by default), CA issuers only, unit, integration and e2e tests, docs on cert-manager.io.
- **Beta:** at least one release of alpha feedback; decisions on the open questions below; metrics and events reviewed; Vault support if agreed.
- **GA:** opt-in moved from annotation to API field if agreed; stable for two releases.

Open questions:

1. Should the opt-in become a field on the Issuer spec (for example `spec.podCertificates.enabled`) at beta?
2. Should other identity formats be supported (for example DNS SANs from the service name, or a configurable template), or should SPIFFE remain the only format?
3. Which issuer types beyond CA should be supported, and in which order?
4. Should [approver-policy](https://cert-manager.io/docs/policy/approval/approver-policy/) be able to restrict which service accounts may use an issuer for pod certificates, or is the per-namespace Issuer plus opt-in enough?

### Upgrade / Downgrade Strategy

The feature is off by default. Enabling it only adds a controller and RBAC. Disabling it stops signing new PCRs; pods keep their current certificates until they expire, and the kubelet keeps retrying the pending requests.

### Supported Versions

Kubernetes 1.37 and later, where `PodCertificateRequest` is GA with `stubPKCS10Request`. On older clusters, the controller logs that the API is unavailable and stays idle, even with the feature gate enabled.

## Production Readiness

- **Metrics:** count of PCRs signed, denied and failed, per issuer, plus signing latency, alongside the existing controller metrics.
- **Events** on the PCR for denial and failure reasons.
- **Logs** at the existing verbosity conventions, including the issuer, the pod and the reason.

## Drawbacks

- A second path for issuing workload certificates next to csi-driver and csi-driver-spiffe, which users have to choose between. The docs will compare them.
- Signing load scales with the number of pods using the volume, rather than with the number of `Certificate` resources.

## Alternatives

- **Use the existing CSR controllers.** A `CertificateSigningRequest` doesn't bind the certificate to a pod or service account identity verified by kube-apiserver, so it can't provide non-impersonable pod identities (see #8378).
- **Translate PCRs into `CertificateRequest`s.** This would reuse every issuer, including external ones, but the identity has to be inside a CSR signed by the pod's private key, which the controller doesn't have. The stub request's contents are chosen by the pod author and can't be trusted.
- **A separate project**, like the existing [pod-certificate-signer](https://github.com/RafPe/pod-certificate-signer) experiments. This would duplicate cert-manager's issuer configuration, credentials handling and CA management, which users already run.
- **Keep using csi-driver-spiffe.** It remains a good choice before 1.37, but needs a CSI driver on every node, while Pod Certificates are built into the kubelet.
