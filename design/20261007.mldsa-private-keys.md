## Summary

cert-manager will support ML-DSA, the NIST post-quantum signature scheme standardised in [FIPS 204][fips204], as a private key algorithm for `Certificate` resources:

```yaml
spec:
  privateKey:
    algorithm: MLDSA
    size: 65 # 44 (default), 65 or 87
```

The implementation uses only the Go standard library (`crypto/mldsa` and the ML-DSA support in `crypto/x509`, both new in Go 1.27). ML-DSA keys can be issued by the SelfSigned and CA issuers, and by their equivalent Kubernetes `CertificateSigningRequest` signers. Other issuers receive the ML-DSA CSR unchanged and the signing CA decides whether to accept it. The feature is opt-in: it sits behind an alpha feature gate and is never the default.

All ML-DSA code lives in files with the `go1.27` build tag. cert-manager's own binaries are built with Go 1.27, so they support ML-DSA. Projects that import cert-manager as a Go library can stay on Go 1.26 if they don't need ML-DSA.

[fips204]: https://nvlpubs.nist.gov/nistpubs/FIPS/NIST.FIPS.204.pdf

## Motivation

The cert-manager [roadmap][roadmap] says: *"cert-manager will adopt PQC in time, as algorithms are further standardised and as solid libraries become available for use."* Both conditions are now met:

- **Standardised:** FIPS 204 was published in August 2024. The X.509 profile for ML-DSA is [RFC 9881][rfc9881].
- **Solid library:** Go 1.27 (August 2026) ships `crypto/mldsa` and ML-DSA support across `crypto/x509` and `crypto/tls` ([golang/go#77626][go77626]). The implementation itself has been in the tree since Go 1.26, and it is part of the Go FIPS 140-3 module from v1.26.0. cert-manager already builds with Go 1.27.1 (`make/_shared/tools/00_mod.mk`).

There is also outside pressure:

- Regulatory deadlines: France's ANSSI (2027), NSA CNSA 2.0 (2027), NIST IR 8547 (deprecated by 2030, disallowed by 2035) and EU critical infrastructure guidance (2030).
- Chrome's [Quantum-resistant Root Program][cqrp] plans to use ML-DSA-44 primarily.
- Users have asked for this feature in [#8929][i8929], and an earlier community PR ([#8527][pr8527]) prototyped it.

Private PKI managed by cert-manager (service mesh, mTLS, internal ingress) is where organisations can start post-quantum authentication earliest, because they control both ends of the connection.

### Goals

- Users can request ML-DSA-44, ML-DSA-65 or ML-DSA-87 private keys on `Certificate` resources and via Ingress/Gateway annotations.
- Issue ML-DSA certificates with the SelfSigned and CA issuers, including ML-DSA root and intermediate CAs and mixed classical/ML-DSA chains.
- Use only the Go standard library: no third-party crypto and no hand-built ASN.1.
- Library consumers who don't use ML-DSA must not be forced onto Go 1.27.
- The feature is opt-in. Behaviour is unchanged for existing RSA, ECDSA and Ed25519 users.
- Fail clearly, and **never silently fall back** to a classical algorithm.
- Document how to migrate safely, including how to roll back.

### Non-Goals

- **ACME.** No public ACME CA issues ML-DSA certificates today. We will follow Let's Encrypt's plans and the Merkle Tree Certificates work separately.
- **Built-in ML-DSA support for Vault, Venafi or external issuers.** They will pass ML-DSA CSRs through, but we won't guarantee or test that they work.
- **Composite / hybrid certificates** (IETF LAMPS composite ML-DSA), **SLH-DSA** (FIPS 205) and **HashML-DSA** (pre-hash mode).
- **Converting existing Certificates automatically**, or making ML-DSA a default.
- **ML-KEM key exchange.** That's a TLS concern, not a certificate one. Go has enabled `X25519MLKEM768` by default since Go 1.24, so cert-manager's own webhook and metrics endpoints already use it.
- **Subprojects** (csi-driver, istio-csr, trust-manager, cmctl, approver-policy). They will be tracked separately and can reuse the `pkg/util/pki` work.

## Proposal

### User Stories

#### Story 1: post-quantum internal PKI

A platform team runs a CA issuer for service-to-service mTLS. They create an ML-DSA-65 root with a SelfSigned issuer, an ML-DSA-65 intermediate, and ML-DSA-65 leaf certificates for a small set of workloads whose TLS stacks support ML-DSA (Go 1.27, OpenSSL 3.5+). Their existing ECDSA hierarchy keeps running alongside the new one.

#### Story 2: a canary before migrating

A user adds a second `Certificate` with `privateKey.algorithm: MLDSA` and a new `secretName`, and points one test Ingress at it. If a consumer can't handle it, they switch the Ingress back to the original Secret, which cert-manager kept renewing the whole time.

#### Story 3: a library consumer on Go 1.26

An external issuer imports `github.com/cert-manager/cert-manager/pkg/util/pki` and builds with Go 1.26. After upgrading its cert-manager dependency, it still compiles and behaves as before. If it ever receives an ML-DSA CertificateRequest, it fails with a clear error saying ML-DSA needs a Go 1.27 build.

### Notes/Constraints/Caveats

- **Not every consumer can use ML-DSA yet.** cert-manager can write a perfectly valid ML-DSA `kubernetes.io/tls` Secret that an ingress controller, proxy, JVM or load balancer can't load. This is the main operational risk. We handle it through documentation (a parallel canary flow and a compatibility matrix, tracked in VC-61114) rather than code.
- **A mixed chain doesn't give post-quantum authentication.** An ML-DSA leaf signed by an ECDSA CA can still be forged by anyone able to break the CA's ECDSA key. cert-manager will allow it, because it's useful for staged migration, but the docs will say clearly that the whole chain must be ML-DSA.
- **Key format interoperability.** RFC 9881 allows three PKCS#8 private key formats: `seed`, `expandedKey` and `both`. Go writes and reads **seed-only** keys. OpenSSL 3.5+ writes `both` **by default**, and Go rejects that format with a clear error. This matters for users who bring their own CA key to a CA issuer. See [Key generation, encoding and parsing](#key-generation-encoding-and-parsing).
- **FIPS builds.** `crypto/mldsa` is unavailable when built against the Go FIPS 140-3 module v1.0.0, and available from module v1.26.0. Any FIPS-mode distribution of cert-manager needs to select v1.26.0 or later.

### Risks and Mitigations

| Risk | Mitigation |
|---|---|
| Consumers can't load ML-DSA Secrets | Opt-in and gated. The docs recommend a parallel Secret plus a canary, and include a compatibility matrix. |
| Weak or immature implementation (raised in #8929, citing Bernstein's 2026 ML-DSA implementation paper) | We use only the Go standard library implementation, which is maintained by the Go security team and included in the FIPS 140-3 module v1.26.0. The vulnerable implementations in that paper were not Go's (see [Filippo Valsorda's response][fv]). The Go implementation signs with hedged randomness by default, which protects against fault attacks on deterministic signing. |
| A bug in ML-DSA code paths affects classical users | All new code is in separate build-tagged files and type-switch branches, and the existing tests must keep passing unchanged. If the feature gate is off, ML-DSA code is never reached. |
| Library consumers are forced onto Go 1.27 | The `go1.27` build tag plus a stub, and a CI job that builds `pkg/...` with Go 1.26. |
| Some issuer silently re-keys or falls back to a classical algorithm | Key generation is driven entirely by `spec.privateKey` and any error is returned as-is. There's no fallback path. Tests check that an unsupported issuer leaves the Certificate not Ready. |
| Larger objects | Measured in the [appendix](#appendix-prototype-measurements): about 20 KiB at worst for a `tls.crt` with an intermediate, far below the 1 MiB Secret limit. |

[fv]: https://mailarchive.ietf.org/arch/msg/tls/p5j6UCQGBAOblWPAjXb5ycMjxA4/

## Design Details

### API

`cert-manager.io/v1` gets a new key algorithm value and three new signature algorithm values. These are plain strings in `pkg/apis`, so they don't need Go 1.27.

```go
// +kubebuilder:validation:Enum=RSA;ECDSA;Ed25519;MLDSA
type PrivateKeyAlgorithm string

const (
	// ...
	// ML-DSA (FIPS 204) private key algorithm.
	// Requires the MLDSAPrivateKeys feature gate.
	MLDSAKeyAlgorithm PrivateKeyAlgorithm = "MLDSA"
)

// +kubebuilder:validation:Enum=SHA256WithRSA;SHA384WithRSA;SHA512WithRSA;ECDSAWithSHA256;ECDSAWithSHA384;ECDSAWithSHA512;PureEd25519;MLDSA44;MLDSA65;MLDSA87
type SignatureAlgorithm string

const (
	// ...
	MLDSA44 SignatureAlgorithm = "MLDSA44"
	MLDSA65 SignatureAlgorithm = "MLDSA65"
	MLDSA87 SignatureAlgorithm = "MLDSA87"
)
```

- **Parameter set:** the existing `privateKey.size` field takes `44`, `65` or `87`. ECDSA already uses `size` for something other than bit length (the curve: 256/384/521), so this fits the existing pattern. It also keeps a single `algorithm` value, which matches Go's single `x509.MLDSA` public key algorithm. The doc comment on `size` will be updated.
- **Default parameter set:** if `size` is omitted, it's **44**. Go's documentation says *"Most applications should use MLDSA44"*, it's the parameter set the WebPKI is converging on, and it matches cert-manager's habit of defaulting to the smallest widely used secure option (RSA-2048, P-256). Users who need CNSA 2.0 compliance should set `size: 87`. Like RSA and ECDSA, the default is applied when the key is generated, not written into the object.
- **Signature algorithm:** `spec.signatureAlgorithm` describes the signature on the CSR, which is made with the Certificate's own key. For ML-DSA the only allowed value is the one that matches the key's parameter set (for example `size: 65` allows only `MLDSA65`). When it's unset, the matching value is used. This extends the existing `keyAlgToAllowedSigAlgs` check. Only pure ML-DSA is supported.
- **Encoding:** ML-DSA keys are always written as PKCS#8. `encoding: PKCS1`, which is the default, is **ignored** for ML-DSA, exactly as it is for Ed25519 today. Rejecting it would break every manifest that just sets `algorithm: MLDSA`.
- **Webhook validation** (`internal/apis/certmanager/validation/certificate.go`):
  - `size` must be 0, 44, 65 or 87 when `algorithm: MLDSA`.
  - `signatureAlgorithm` must match the parameter set.
  - If the `MLDSAPrivateKeys` gate is disabled, creating a resource with `algorithm: MLDSA`, or changing an existing one to it, is rejected with: `privateKey.algorithm: MLDSA requires the MLDSAPrivateKeys feature gate to be enabled`. An update that leaves an existing `MLDSA` value unchanged is still allowed, so objects created while the gate was on can be edited and deleted after it's turned off.
- **CRD schema:** the CRD enum always includes `MLDSA`, because CRDs can't follow a feature gate. The webhook enforces the gate. This is the same approach as other gated fields such as `nameConstraints` and `otherNames`.

### Go version compatibility: the `go1.27` build tag

The `go` directive stays at `1.26.0` in every `go.mod`. Code that refers to `crypto/mldsa`, or to the `x509.MLDSA*` constants, goes in files built only with Go 1.27 or later. Each has a matching stub for older toolchains:

```
pkg/util/pki/mldsa_go127.go    //go:build go1.27
pkg/util/pki/mldsa_stub.go     //go:build !go1.27
```

The two files expose the same small internal interface. The rest of `pkg/util/pki` calls these functions and never imports `crypto/mldsa` directly:

```go
// MLDSASupported reports whether this binary was built with ML-DSA support (Go >= 1.27).
const MLDSASupported = true // false in the stub

// ErrMLDSAUnsupported is returned by every function below in the stub build.
var ErrMLDSAUnsupported = errors.New("ML-DSA requires cert-manager (or the program importing it) to be built with Go 1.27 or later")

func GenerateMLDSAPrivateKey(size int) (crypto.Signer, error)
func mldsaParameterSet(pub crypto.PublicKey) (size int, ok bool)            // used by match.go, SignCertificate, etc.
func mldsaSignatureAlgorithm(size int) (x509.SignatureAlgorithm, error)     // 44→x509.MLDSA44 ...
```

We confirmed with a prototype (see the appendix) that:

1. A `//go:build go1.27` file in a module declaring `go 1.26.0` **is** compiled by a Go 1.27.1 toolchain, and can use `crypto/mldsa`. Since Go 1.21, a build constraint like this also raises that file's language version.
2. The same module built with Go 1.26.5 uses the stub, and returns `ErrMLDSAUnsupported` at runtime instead of failing to compile.
3. No GODEBUG setting controls ML-DSA in Go 1.27, so leaving the `go` directive at 1.26 doesn't silently turn ML-DSA off in our binaries. (Moving the directive to 1.27 would change other defaults, such as `x509sslcertoverrideplatform`. That's another reason not to move it.)

Notes for implementers:

- **Go 1.26 parsing behaviour.** On Go 1.26, `x509.ParseCertificate` of an ML-DSA certificate *succeeds*, but `PublicKey == nil` and `PublicKeyAlgorithm == UnknownPublicKeyAlgorithm`. `ParsePKCS8PrivateKey` returns an "unknown algorithm" error, and `CSR.CheckSignature` returns "algorithm unimplemented". Any `pkg/util/pki` function that type-switches on public keys (`PublicKeysEqual`, `SignCertificate`, and others) must return an error for a `nil` or unknown key, never panic. Unit tests will cover this in the Go 1.26 CI job.
- `pkg/apis/...` and `internal/apis/...` must not import the build-tagged code. Validation works only on strings.
- We'll add a CI target that builds and unit-tests `./pkg/...` and `./internal/...` with the oldest supported Go toolchain, currently Go 1.26, so the promise is enforced.

### Key generation, encoding and parsing

- `pkg/util/pki/generate.go`: `GeneratePrivateKeyForCertificate` gets a `case v1.MLDSAKeyAlgorithm` that calls `GenerateMLDSAPrivateKey(size)`, with `0` meaning 44. Unsupported sizes return an error.
- `EncodePrivateKey`: `*mldsa.PrivateKey` → `x509.MarshalPKCS8PrivateKey` → a `PRIVATE KEY` PEM block, whatever `encoding` says. This is a **seed-only** PKCS#8 key: 54 bytes DER, 128 bytes PEM.
- Parsing (`internal/pem`, `pkg/util/pki/parse.go`): `x509.ParsePKCS8PrivateKey` already returns `*mldsa.PrivateKey` for seed-only keys. No custom ASN.1 is needed.
- **Keys from OpenSSL (CA issuer).** OpenSSL 3.5+'s `genpkey -algorithm ML-DSA-65` writes the `both` (seed + expanded) format by default. Go rejects it with: `ML-DSA private keys with both seed and expanded key are not supported, use e.g. "openssl pkey -provparam ml-dsa.output_formats=seed-only" to convert to a seed-only key`. We'll show this error in the CA Issuer's `Ready` condition and document the conversion command. We will **not** write our own parser for the `both` or `expandedKey` formats. Doing that safely means checking that the expanded key matches the seed, which is security-sensitive work that belongs in the standard library. If Go adds support later, cert-manager gets it for free.
- `pkg/util/pki/match.go`: `PrivateKeyMatchesSpec` gets an ML-DSA branch that checks the key type and that its parameter set equals `size`, or 44 if `size` is 0. `PublicKeysEqual` works as-is because `*mldsa.PublicKey` implements `Equal`.

### CSRs, signing and mixed chains

- `GenerateCSR` / `EncodeCSR`: `x509.CreateCertificateRequest` accepts `*mldsa.PrivateKey`. `SignatureAlgorithm(crt)` gets ML-DSA entries in `keyAlgorithms` and `sigAlgorithms`. The `x509.MLDSA*` values are added from the build-tagged file in an `init()`, because the constants don't exist in Go 1.26.
- CSR verification (`certificatetemplate.go`): `CheckSignature` works unchanged on Go 1.27.
- `SignCertificate`: the type switch on the signer's public key gets an ML-DSA case, via `mldsaParameterSet`. `signatureAlgorithmFromPublicKey` maps it to `x509.MLDSA44/65/87`. As today, the **issuer's** key decides the certificate's signature algorithm, so mixed chains need no special handling:
  - an ML-DSA leaf under an ECDSA CA is signed with `ECDSA-SHA256`
  - an ECDSA leaf under an ML-DSA CA is signed with `ML-DSA-65`
- `ca.crt` handling is unchanged.

### Issuers

| Issuer | Behaviour |
|---|---|
| SelfSigned | Supported. Works through `SignCertificate`. |
| CA (and ClusterIssuer) | Supported, with an ML-DSA or classical CA keypair. The Issuer's `Ready` condition shows key-parsing errors (for example the OpenSSL `both` format). |
| Kubernetes CSR signers (`issuers.cert-manager.io/*`, `clusterissuers.cert-manager.io/*`) for SelfSigned/CA | Supported. They share the `pkg/util/pki` code. |
| ACME, Vault, Venafi/NGTS, external issuers | **Not blocked by cert-manager.** The ML-DSA CSR is sent unchanged and the CA accepts or rejects it. A rejection shows up as a failed CertificateRequest, exactly as it does today for Ed25519 CSRs sent to CAs that don't support Ed25519. Nothing ever re-keys with a classical algorithm. Not tested in v1, and documented as unsupported. |

We chose pass-through over blocking on purpose. It's consistent with how Ed25519 is handled, it leaves private ACME/Vault/external CAs free to add ML-DSA support without a cert-manager release, and blocking wouldn't make anything safer, because the CA rejecting the CSR is already a clear failure.

### Certificate lifecycle

- **Re-issuance triggers** (`internal/controller/certificates/policies/checks.go`): these work through `PrivateKeyMatchesSpec`. Changing the algorithm (for example RSA → MLDSA) or the parameter set (for example 65 → 87) triggers re-issuance. With `rotationPolicy: Never` it raises the existing "key does not match spec" condition and waits for the user.
- `rotationPolicy: Always` / `Never`, renewal, controller restart and reconciling from an existing Secret all work through the paths above, and integration tests will cover them.
- **Feature gate disabled in the controller.** For a Certificate with `algorithm: MLDSA` (created while the gate was on), the controller won't generate keys or issue. It sets `Issuing=False` with reason `MLDSAPrivateKeysDisabled` and an explanatory message, and **leaves the existing Secret alone**: no deletion, so workloads keep running until the certificate expires.
- **Binary built without Go 1.27** (forks, downstream builds): key generation returns `ErrMLDSAUnsupported`, which shows up as an `Issuing=False` condition.

### Ingress and Gateway annotations

`pkg/controller/certificate-shim/helper.go` accepts `cert-manager.io/private-key-algorithm: MLDSA`, and `cert-manager.io/private-key-size: 44|65|87`, through the same validation. Invalid values give the existing "invalid ingress annotation" event and no Certificate.

### Additional output formats and keystores

- `CombinedPEM` and `DER` output formats work unchanged.
- **PKCS#12:** `software.sslmate.com/src/go-pkcs12` (v0.7.3) uses `x509.MarshalPKCS8PrivateKey`, so with the `Modern2026`/`Modern2023` profiles it encodes ML-DSA keys correctly. In the prototype, OpenSSL 3.6 read the result back fine.
- **JKS:** `keystore-go` stores the PKCS#8 DER from `x509.MarshalPKCS8PrivateKey`, so encoding succeeds. Whether a JVM can load it depends on the Java version (JDK 24+ has ML-DSA via JEP 497). We'll check this in the interop spike.
- Both keystores are **allowed** in v1, with a documented note that consumer support varies. We won't block something that works.

### Size limits

`internal/pem` limits are derived from `maxCACertificatePEMSize = 6500` bytes. An ML-DSA-65 root (7525 bytes) or ML-DSA-87 root (10178 bytes) goes over that *estimate*, but the constant isn't enforced on its own. What's actually enforced is:

- a single certificate: 36.5 KB
- a chain: 95 KB
- a bundle: 330 KB

All realistic ML-DSA chains fit; a full ML-DSA-87 root + intermediate + leaf is about 30 KB. A pathological 10-certificate ML-DSA-87 chain (about 100 KB) would go over the chain limit. For v1 we will **not** change the limits. We'll update the comment to describe ML-DSA sizes and add a unit test proving that a 4-deep ML-DSA-87 chain parses. Operators can still raise the limits through the existing configuration (`NewSizeLimitsFromConfig`).

### Test Plan

**Unit** (`pkg/util/pki`, `internal/pem`, validation, `certificate-shim`):
- Generate, encode, parse, CSR, sign and verify round trips for ML-DSA-44/65/87.
- Mixed chains in both directions. Root → intermediate → leaf verification with `x509.Verify`.
- Negative cases:
  - malformed or truncated PEM
  - a CSR with a bad signature
  - unsupported sizes
  - a signatureAlgorithm that doesn't match the key
  - an OpenSSL `both`-format key, which must give the Go error message
- Validation tests with the gate on and off, including the update-ratcheting case.
- `PrivateKeyMatchesSpec` / `checks.go` for algorithm changes and 65 → 87.
- **A Go 1.26 CI job** that builds `./pkg/... ./internal/...` and runs the unit tests with the stub, including the "nil PublicKey on an ML-DSA cert never panics" cases.
- Port the useful vectors from #8527's `parse_test.go`, crediting the original author.

**Integration** (`test/integration`): issuing and renewal with `rotationPolicy` Never and Always, controller restart, the gate disabled while an ML-DSA Certificate exists, PKCS#12/JKS/CombinedPEM output.

**E2E** (`test/e2e`):
- Add `featureset.MLDSAFeatureSet`.
- Add ML-DSA cases to the Certificates and CertificateSigningRequests conformance suites, and mark the feature unsupported for the ACME, Vault, Venafi, NGTS and external suites.
- SelfSigned/CA chain scenarios.
- Enable the gate in the e2e cluster.

**Interop** (not in CI, tracked in VC-61114): a compatibility matrix for ingress-nginx, Envoy/Istio, OpenSSL, JVM and Go TLS. The prototype already confirmed that Go 1.27 ↔ Go 1.27 and Go server ↔ OpenSSL 3.6 `s_client` TLS 1.3 handshakes succeed with ML-DSA certificates.

### Graduation Criteria

**Alpha (v1.22)**, gate `MLDSAPrivateKeys` defaults to off:
- Implemented for SelfSigned, CA and the Kubernetes CSR signers. Unit, integration and e2e tests pass.
- Go 1.26 library build job in CI.
- Docs published, including the canary migration guide and known limitations.

**Beta**, default on:
- At least one release cycle as alpha with no ML-DSA-specific bugs open.
- User feedback from at least 2 adopters running ML-DSA in production or staging.
- The compatibility matrix covers the major ingress, mesh and proxy implementations.
- The OpenSSL key format question has been reviewed again, based on what Go supports at the time.

**GA**:
- Two releases at beta with no significant issues.
- The minimum Go toolchain for cert-manager library consumers is at least 1.27, at which point the build tag and stub can be removed.

### Upgrade / Downgrade Strategy

- **Upgrade:** no effect until the gate is enabled and a user sets `algorithm: MLDSA`.
- **Downgrade to a version without ML-DSA support:** the older CRD enum doesn't include `MLDSA`. Existing objects stay stored but can't be updated. The older controller will treat them as having an unsupported algorithm and stop renewing them. Users must first switch ML-DSA Certificates to a classical algorithm, or delete them. Release notes and docs will say so. Workloads keep running on the existing Secrets until the certificates expire.
- **Disabling the gate:** see [Certificate lifecycle](#certificate-lifecycle). Existing Secrets are kept, renewal stops, and the condition explains why.

### Supported Versions

- Kubernetes: every version supported by the cert-manager release. Nothing here depends on Kubernetes.
- Go: cert-manager binaries are built with Go 1.27.1+. Library consumers can use Go 1.26 (without ML-DSA) or Go 1.27+ (with ML-DSA).
- FIPS: Go FIPS 140-3 module v1.26.0 or later is required for ML-DSA.

## Production Readiness

### How can this feature be enabled / disabled for an existing cert-manager installation?

Set `--feature-gates=MLDSAPrivateKeys=true` on both the controller and the webhook (`featureGates` and `webhook.featureGates` in Helm). Turning it off later is safe. Existing ML-DSA Secrets are kept, no new ML-DSA keys are issued, affected Certificates report `Issuing=False` with reason `MLDSAPrivateKeysDisabled`, and the webhook still lets users edit or delete those Certificates. Tests cover both gate states.

### Does this feature depend on any specific services running in the cluster?

No. Whether workloads can *use* the issued certificates depends on the consumer (see Caveats).

### Will enabling / using this feature result in new API calls (i.e to Kubernetes apiserver or external services)?

No. Issuance follows the existing flow.

### Will enabling / using this feature result in increasing size or count of the existing API objects?

There are no new objects, but objects using ML-DSA are bigger:
- Per certificate, `CertificateRequest.spec.request` is about 5–10 KB.
- Per leaf + intermediate, `CertificateRequest.status.certificate` and `tls.crt` are about 11–20 KB.
- `tls.key` is smaller than RSA (128 bytes).

The CRD schema grows by 4 enum values.

### Will enabling / using this feature result in significant increase of resource usage? (CPU, RAM...)

No. Generating and signing ML-DSA keys is faster than RSA-2048 key generation. The slightly bigger cached Secrets add negligible memory.

## Drawbacks

- Users can now create Secrets that some of their consumers can't load. This is mitigated by the gate, the opt-in model and the documentation.
- More code paths to maintain, plus the build-tag split, until the minimum Go version for library consumers reaches 1.27.
- Reusing `size` for parameter sets is slightly overloaded, though ECDSA set the precedent.

## Alternatives

1. **Merge #8527 as-is, using `cloudflare/circl` and hand-built ASN.1.** Rejected. It goes against the roadmap's preference for the standard library, adds a crypto dependency, and duplicates encoding logic that the standard library now provides and tests. We'll reuse its structure and test ideas, with attribution.
2. **Separate enum values `MLDSA44`/`MLDSA65`/`MLDSA87` for `privateKey.algorithm`.** Simpler validation, but `size` would be ignored (as for Ed25519) and there would be three algorithm values for one x509 public key algorithm. We chose `algorithm: MLDSA` plus `size` to match how ECDSA works and to keep the algorithm enum short. This is still open for maintainers to decide.
3. **A dedicated `parameterSet` field.** Adds API surface for very little gain over `size`.
4. **Raise the `go` directive to 1.27 everywhere.** Simpler code, but it would force every downstream importer of cert-manager onto Go 1.27 immediately, and change Go 1.27 GODEBUG defaults for our binaries. Rejected in favour of the build tag.
5. **Block ML-DSA for non-SelfSigned/CA issuers.** Rejected. It's inconsistent with Ed25519, and it would stop private CAs that do support ML-DSA. A CA rejection is already a clear failure.
6. **Default parameter set 65 (NIST category 3).** A reasonable choice for maintainers to consider. We propose 44 for the reasons given in [API](#api).

## Appendix: prototype measurements

Measured on 2026-10-07 with Go 1.27.1 (darwin/arm64) and OpenSSL 3.6.4. The prototype was a throwaway module declaring `go 1.26.0`, with a `go1.27`-tagged ML-DSA file and a `!go1.27` stub.

| | ML-DSA-44 | ML-DSA-65 | ML-DSA-87 |
|---|---|---|---|
| Public key / signature (bytes) | 1312 / 2420 | 1952 / 3309 | 2592 / 4627 |
| `tls.key` PEM, PKCS#8 seed-only | 128 B | 128 B | 128 B |
| `tls.crt` PEM, leaf + intermediate | 10,956 B | 15,099 B | 20,405 B |
| `ca.crt` PEM, root | 5,454 B | 7,525 B | 10,178 B |
| CSR PEM | 5,275 B | 7,346 B | 9,999 B |
| CSR `CheckSignature`, chain `Verify`, PKCS#8 round trip | ok | ok | ok |
| Go ↔ Go TLS 1.3 handshake | ok | ok | ok |

Other results:
- Go server with an ML-DSA-65 certificate ↔ `openssl s_client`: TLS 1.3, peer signature `mldsa65`, group `X25519MLKEM768`, verify OK.
- OpenSSL reads Go-generated ML-DSA certificates and keys, and `openssl verify` passes.
- Go reads OpenSSL keys as follows: `seed-only` ✅, `priv-only` ❌ (not supported), `seed-priv` (OpenSSL's default) ❌ with an error suggesting the conversion command.
- PKCS#12 (`go-pkcs12` `Modern2026`) encodes and decodes an ML-DSA key, and `openssl pkcs12` reads it. JKS (`keystore-go`) encodes it; JVM loading is untested.
- Go 1.26.5 with the same module uses the stub. Parsing ML-DSA material with Go 1.26:
  - a certificate parses with `PublicKey=nil`
  - a PKCS#8 key gives an "unknown algorithm" error
  - CSR `CheckSignature` gives "algorithm unimplemented"

## Appendix: answers to the questions raised in #8929

1. ***Is `algorithm: MLDSA` with `size: 44|65|87` consistent with the desired long-term API?*** Yes. This design proposes exactly that (see [API](#api) and [Alternatives](#alternatives) 2–3), and maintainers have the final say.
2. ***Feature gate, and CRD behaviour when the gate is disabled?*** Alpha gate `MLDSAPrivateKeys` on both the controller and the webhook. The CRD enum always includes `MLDSA`, and the webhook rejects new uses while the gate is off but allows existing values to stay unchanged on update.
3. ***Rework #8527 or start a new standard-library PR?*** Start new standard-library PRs, split into small pieces (API → PKI → issuers → controller → shim → e2e). We'll offer the #8527 author the chance to co-author or rework, credit them with `Co-authored-by`, and port their tests.
4. ***Consumer interoperability tests in-tree, or stop at valid X.509 output plus a documented canary process?*** In-tree tests stop at valid X.509/Secret output plus Go TLS handshakes. Consumer compatibility goes in a documented matrix (VC-61114) and the canary guide, not in CI.
