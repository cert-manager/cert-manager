## Summary

cert-manager will support ML-DSA, the NIST post-quantum signature scheme standardised in [FIPS 204][fips204], as a private key algorithm for `Certificate` resources:

```yaml
spec:
  privateKey:
    algorithm: MLDSA
    size: 65 # 44 (default), 65 or 87
```

The implementation uses only the Go standard library (`crypto/mldsa` and the ML-DSA support in `crypto/x509`, both new in Go 1.27). ML-DSA certificates can be issued by the SelfSigned and CA issuers, and by their equivalent Kubernetes `CertificateSigningRequest` signers (which are themselves behind the existing `ExperimentalCertificateSigningRequestControllers` gate). Other issuers receive the ML-DSA CSR unchanged and the signing CA decides whether to accept it. The feature is opt-in: users must ask for ML-DSA on each Certificate, and it's never the default algorithm. It sits behind a feature gate, which is alpha (off by default) in v1.22.

cert-manager's `go.mod` files move to Go 1.27, so the code uses `crypto/mldsa` directly. The implementation builds on the community PR [#8527][pr8527], which already uses the standard library, rather than replacing it.

[fips204]: https://nvlpubs.nist.gov/nistpubs/FIPS/NIST.FIPS.204.pdf

## Motivation

The cert-manager [roadmap][roadmap] says: *"cert-manager will adopt PQC in time, as algorithms are further standardised and as solid libraries become available for use."* Both conditions are now met:

- **Standardised:** FIPS 204 was published in August 2024. The X.509 profile for ML-DSA is [RFC 9881][rfc9881].
- **Solid library:** Go 1.27 (August 2026) ships `crypto/mldsa` and ML-DSA support across `crypto/x509` and `crypto/tls` ([golang/go#77626][go77626]). The implementation itself has been in the tree since Go 1.26. cert-manager already builds with Go 1.27.1 (`make/_shared/tools/00_mod.mk`).

There is also outside pressure:

- Regulatory deadlines: France's ANSSI (2027), NSA CNSA 2.0 (2027), NIST IR 8547 (deprecated by 2030, disallowed by 2035) and EU critical infrastructure guidance (2030).
- Chrome's [Quantum-resistant Root Program][cqrp] plans to use ML-DSA-44 primarily.
- Users have asked for this feature in [#8929][i8929], and a community PR ([#8527][pr8527]) already implements much of it.

Private PKI managed by cert-manager (service mesh, mTLS, internal ingress) is where organisations can start post-quantum authentication earliest, because they control both ends of the connection.

### Goals

- Users can request ML-DSA-44, ML-DSA-65 or ML-DSA-87 private keys on `Certificate` resources and via Ingress/Gateway annotations.
- Issue ML-DSA certificates with the SelfSigned and CA issuers, including ML-DSA root and intermediate CAs and mixed classical/ML-DSA chains.
- Use only the Go standard library: no third-party crypto and no hand-built ASN.1.
- The feature is opt-in. Behaviour is unchanged for existing RSA, ECDSA and Ed25519 users.
- Fail clearly, and **never silently fall back** to a classical algorithm.
- Document how to migrate safely, including how to roll back.

### Non-Goals

- **ACME.** No public ACME CA issues ML-DSA certificates today. We will follow Let's Encrypt's plans and the Merkle Tree Certificates work separately.
- **Built-in ML-DSA support for Vault, Venafi or external issuers.** They will pass ML-DSA CSRs through, but we won't guarantee or test that they work.
- **Composite / hybrid certificates** (IETF LAMPS composite ML-DSA), **SLH-DSA** (FIPS 205) and **HashML-DSA** (pre-hash mode).
- **Converting existing Certificates automatically**, or making ML-DSA a default.
- **ML-KEM key exchange.** That's a TLS concern, not a certificate one. Go has enabled `X25519MLKEM768` by default since Go 1.24, and cert-manager doesn't override the curve preferences, so its own webhook and (when TLS is enabled) metrics endpoints already use it.
- **Subprojects** (csi-driver, istio-csr, trust-manager, cmctl, approver-policy). They will be tracked separately. They can reuse the exported `pkg/util/pki` functions once those support ML-DSA.
- **Recording the key algorithm on the Secret.** cert-manager doesn't annotate Secrets with the key algorithm today (only the subject and SANs), and this design doesn't change that.

## Proposal

### User Stories

#### Story 1: post-quantum internal PKI

A platform team runs a CA issuer for service-to-service mTLS. They create an ML-DSA-65 root with a SelfSigned issuer, an ML-DSA-65 intermediate, and ML-DSA-65 leaf certificates for a small set of workloads whose TLS stacks support ML-DSA (Go 1.27, OpenSSL 3.5+). Their existing ECDSA hierarchy keeps running alongside the new one.

#### Story 2: a canary before migrating

A user adds a second `Certificate` with `privateKey.algorithm: MLDSA` and a new `secretName`, and points one test Ingress at it. If a consumer can't handle it, they switch the Ingress back to the original Secret, which cert-manager kept renewing the whole time.

### Notes/Constraints/Caveats

- **Not every consumer can use ML-DSA yet.** cert-manager can write a perfectly valid ML-DSA `kubernetes.io/tls` Secret that an ingress controller, proxy, JVM or load balancer can't load. This is the main operational risk. We handle it through documentation (a parallel canary flow and a compatibility matrix, tracked in a follow-up issue) rather than code.
- **A mixed chain doesn't give post-quantum authentication.** An ML-DSA leaf signed by an ECDSA CA can still be forged by anyone able to break the CA's ECDSA key. cert-manager will allow it, because it's useful for staged migration, but the docs will say clearly that the whole chain must be ML-DSA.
- **Key format interoperability.** RFC 9881 allows three PKCS#8 private key formats: `seed`, `expandedKey` and `both`. Go writes and reads **seed-only** keys. OpenSSL 3.5+ writes `both` **by default**, and Go rejects that format with a clear error. This matters for users who bring their own CA key to a CA issuer. See [Key generation, encoding and parsing](#key-generation-encoding-and-parsing).
- **Go 1.27 already changes behaviour without this feature.** `master` is built with Go 1.27, so `crypto/x509` parses ML-DSA keys, certificates and CSRs even though cert-manager has no ML-DSA support. This depends on the toolchain, not on the `go` directive. Without the gate checks, v1.22 would be the first release to accept ML-DSA CSRs in CertificateRequests and to let an RSA, ECDSA or Ed25519 CA issuer sign them, with no feature gate involved. v1.21 is built with Go 1.26, so it rejects those CSRs at admission (`algorithm unimplemented`). The gate therefore has to cover these paths too, not just key generation (see [Issuers](#issuers)), and the gate checks must land before v1.22 is cut. If the ML-DSA work looks like missing v1.22, a small change will reject ML-DSA CSRs and keys instead, to keep the v1.21 behaviour.

### Risks and Mitigations

| Risk | Mitigation |
|---|---|
| Consumers can't load ML-DSA Secrets | Opt-in per Certificate, and gated while alpha. The docs recommend a parallel Secret plus a canary, and include a compatibility matrix. |
| Weak or immature implementation (raised in #8929, citing Bernstein's 2026 ML-DSA implementation paper) | We use only the Go standard library implementation, which is maintained by the Go security team. As far as we can tell, the paper's findings don't apply to Go's implementation (see [Filippo Valsorda's response][fv]). The Go implementation signs with hedged randomness by default, which protects against fault attacks on deterministic signing. |
| A bug in ML-DSA code paths affects classical users | All new code is in separate type-switch branches, and the existing tests must keep passing unchanged. With the gate off, cert-manager never generates ML-DSA keys or signs ML-DSA certificates. (Some shared code, such as `DecodePrivateKeyBytes`, already returns ML-DSA keys on Go 1.27 whatever the gate says, so those paths must fail safely with an error.) |
| Projects that import cert-manager as a library must move to Go 1.27 | Accepted. We avoid breaking library consumers where we can, but cert-manager itself comes first, and Go 1.27 is the current Go release. |
| Some issuer silently re-keys or falls back to a classical algorithm | Key generation is driven entirely by `spec.privateKey` and any error is returned as-is. There's no fallback path. Tests check that an unsupported issuer leaves the Certificate not Ready. |
| Larger objects | Measured in the [appendix](#appendix-prototype-measurements): about 20 KiB at worst for a `tls.crt` with an intermediate, far below the 1 MiB Secret limit. |

[fv]: https://mailarchive.ietf.org/arch/msg/tls/p5j6UCQGBAOblWPAjXb5ycMjxA4/

## Design Details

### API

`cert-manager.io/v1` gets one new key algorithm value. There are no new signature algorithm values (see below).

```go
// +kubebuilder:validation:Enum=RSA;ECDSA;Ed25519;MLDSA
type PrivateKeyAlgorithm string

const (
	// ...
	// ML-DSA (FIPS 204) private key algorithm.
	// Requires the MLDSAPrivateKeys feature gate.
	MLDSAKeyAlgorithm PrivateKeyAlgorithm = "MLDSA"
)
```

- **Parameter set:** the existing `privateKey.size` field takes `44`, `65` or `87`. ECDSA already uses `size` for something other than bit length (the curve: 256/384/521), so this fits the existing pattern. It also keeps a single `algorithm` value, which matches Go's single `x509.MLDSA` public key algorithm. The doc comment on `size` will be updated.
- **Default parameter set:** if `size` is omitted, it's **44**, which maintainers have said looks sensible. Go's documentation says *"Most applications should use MLDSA44"*, it's the parameter set the WebPKI is converging on, and it matches cert-manager's habit of defaulting to the smallest widely used secure option (RSA-2048, P-256). Users who need CNSA 2.0 compliance should set `size: 87`. Like RSA and ECDSA, the default is applied when the key is generated, not written into the object.
- **No signature algorithm values:** `spec.signatureAlgorithm` only controls the signature on the CSR, which is made with the Certificate's own key. For RSA and ECDSA that's a real choice (the hash function). For an ML-DSA key there's only one correct value: an ML-DSA-44 key can only make ML-DSA-44 signatures. The signature on the issued certificate is decided by the *signer's* key, not by anything in the Certificate spec. A user-facing value would therefore be useless at best and a footgun at worst, so we don't add `MLDSA44`/`MLDSA65`/`MLDSA87` values (see [Alternatives](#alternatives) 4). `spec.signatureAlgorithm` must be left unset for ML-DSA, and cert-manager uses the parameter set that matches the key.
- **Encoding:** ML-DSA keys are always written as PKCS#8. `encoding: PKCS1`, which is the default, is **ignored** for ML-DSA, exactly as it is for Ed25519 today. Rejecting it would break every manifest that just sets `algorithm: MLDSA`.
- **Webhook validation** (`internal/apis/certmanager/validation/certificate.go`):
  - `size` must be 0, 44, 65 or 87 when `algorithm: MLDSA`.
  - `signatureAlgorithm` must be unset when `algorithm: MLDSA`, with an error that says the signature algorithm follows from the key's parameter set. This needs an explicit check: today, a key algorithm with no entry in `keyAlgToAllowedSigAlgs` accepts *any* signature algorithm, so leaving ML-DSA out of the map would let, for example, `SHA256WithRSA` through to the controller.
  - If the `MLDSAPrivateKeys` gate is disabled, creating a resource with `algorithm: MLDSA`, or changing an existing one to it, is rejected with: `privateKey.algorithm: MLDSA requires the MLDSAPrivateKeys feature gate to be enabled`. An update that leaves an existing `MLDSA` value unchanged is still allowed, so objects created while the gate was on can be edited and deleted after it's turned off. The webhook validates every CREATE and UPDATE, including status updates, so without this the controller couldn't even update the status of such a Certificate. The validation functions already receive the old object; `renewBeforePercentage` uses it (`oldCrt`) in the same way.
  - **CertificateRequests:** if the gate is disabled, the webhook rejects a CertificateRequest whose CSR has an ML-DSA public key. This keeps the v1.21 behaviour, where Go 1.26's `CheckSignature` rejected these CSRs (see [Caveats](#notesconstraintscaveats)). Update validation doesn't re-check the CSR, so existing CertificateRequests are never stuck.
- **CRD schema:** the CRD enum always includes `MLDSA`, because CRDs can't follow a feature gate. The webhook enforces the gate. Other gated fields, such as `nameConstraints` and `otherNames`, are also enforced only by the webhook, but they don't keep existing values valid after the gate is turned off. `MLDSA` has to, for the reason above.
- **Gate registration:** the gate is added to `internal/controller/feature` and `internal/webhook/feature`, and enabled in the e2e cluster through `feature_gates_controller` and `feature_gates_webhook` in `make/e2e-setup.mk`.

### Go version

`crypto/mldsa` and the `x509.MLDSA*` constants are new in Go 1.27, so the `go` directive moves from `1.26.0` to `1.27.0` in every `go.mod`. cert-manager is already built with Go 1.27.1, so this only changes:

- **Library consumers**, who need Go 1.27 to build against cert-manager. We avoid breaking them where we can, but cert-manager itself comes first, and we don't treat the `go` directive as part of the library's compatibility promise.
- **GODEBUG defaults**, which follow the `go` directive. Between Go 1.26 and 1.27 two defaults change. `tracebacklabels` only affects tracebacks. `x509sslcertoverrideplatform` makes `SSL_CERT_FILE`/`SSL_CERT_DIR` override the platform verifier, but only on macOS and Windows; cert-manager's images are Linux. No GODEBUG setting controls ML-DSA.
- **Linting**: golangci-lint's `modernize` linter gains an `embedlit` check for Go 1.27, which reports over 800 struct literals that could omit embedded field types. The bump PR disables that check, and a separate mechanical PR can apply the fixes.

The bump is a small standalone PR, which can merge independently of the ML-DSA work. It doesn't change how cert-manager handles ML-DSA, because that depends on the toolchain, which is already Go 1.27 (see [Caveats](#notesconstraintscaveats)). #8527 also moves the `go` directive to 1.27. Whichever PR merges first makes that change, and the other is rebased.

### Relationship to #8527

[#8527][pr8527] adds ML-DSA keys using the standard library, and also moves the `go` directive to 1.27. Rather than replacing it, we propose to work with its author to finish it, or to split it into smaller PRs with them credited as co-author if maintainers prefer. Compared with this design, it still needs:

- `algorithm: MLDSA` with `size: 44|65|87`, instead of the separate `MLDSA44`/`MLDSA65` algorithm values (see [Alternatives](#alternatives) 2)
- no ML-DSA signature algorithm values: #8527's `PureMLDSA44`/`PureMLDSA65` are dropped (see [API](#api))
- ML-DSA-87
- the public-key mismatch checks in `checks.go` restored, by making `PublicKeysEqual` and `PublicKeyForPrivateKey` handle ML-DSA (see [below](#key-generation-encoding-and-parsing)); #8527 currently comments them out
- the `MLDSAPrivateKeys` feature gate and the webhook validation described in [API](#api)
- tests, which are the main missing piece

### Key generation, encoding and parsing

- `pkg/util/pki/generate.go`: `GeneratePrivateKeyForCertificate` gets a `case v1.MLDSAKeyAlgorithm` that calls `mldsa.GenerateKey` with the parameter set for `size` (`mldsa.MLDSA44()`, `MLDSA65()` or `MLDSA87()`), with `0` meaning 44. Unsupported sizes return an error.
- `EncodePrivateKey`: `*mldsa.PrivateKey` → `x509.MarshalPKCS8PrivateKey` → a `PRIVATE KEY` PEM block, whatever `encoding` says. This is a **seed-only** PKCS#8 key: 54 bytes DER, 128 bytes PEM.
- Parsing (`internal/pem`, `pkg/util/pki/parse.go`): `x509.ParsePKCS8PrivateKey` already returns `*mldsa.PrivateKey` for seed-only keys. No custom ASN.1 is needed.
- **Keys from OpenSSL (CA issuer).** OpenSSL 3.5+'s `genpkey -algorithm ML-DSA-65` writes the `both` (seed + expanded) format by default. Go rejects it with: `x509: ML-DSA private keys with both seed and expanded key are not supported, use e.g. "openssl pkey -provparam ml-dsa.output_formats=seed-only" to convert to a seed-only key`. An expanded-only key gives `x509: semi-expanded ML-DSA private keys without seed are not supported`. The CA issuer shows these errors in its `Ready` condition (reason `ErrGetKeyPair`), and we'll document the conversion command. Unit tests will check both messages, so we notice if Go changes them. We will **not** write our own parser for the `both` or `expandedKey` formats. Doing that safely means checking that the expanded key matches the seed, which is security-sensitive work that belongs in the standard library. If Go adds support later, cert-manager gets it for free.
- `pkg/util/pki/match.go`: `PrivateKeyMatchesSpec` gets an ML-DSA branch that checks the key type and that its parameter set equals `size`, or 44 if `size` is 0. Its `default` branch panics on an unknown algorithm today. As a defensive fix, the implementation changes it to report a violation instead, because the controllers have no panic recovery: one Certificate with an algorithm the controller doesn't know about (for example after a downgrade) would crash-loop the controller for every Certificate. Users can't trigger this directly, because the CRD enum and the webhook both reject unknown algorithms, so the fix isn't backported.
- **Key comparison helpers need changes.** `PublicKeysEqual` and `PublicKeyForPrivateKey` type-switch on RSA, ECDSA and Ed25519, and return an error for anything else, so today they fail for ML-DSA keys. Both need to handle ML-DSA, either with a `*mldsa.PublicKey` case (as #8527 does for `PublicKeysEqual`) or, more simply, with a generic fallback on the standard `Equal(crypto.PublicKey) bool` and `Public() crypto.PublicKey` methods, which `*mldsa.PublicKey` and `*mldsa.PrivateKey` implement. Callers that depend on this include:
  - the re-issuance checks (`internal/controller/certificates/policies/checks.go`)
  - the issuing and request manager controllers
  - the SelfSigned issuer, for CertificateRequests and CertificateSigningRequests
  - the ACME and Vault issuers, which check the issued certificate against the CSR (so even pass-through needs this)

### CSRs, signing and mixed chains

- `GenerateCSR` / `EncodeCSR`: `x509.CreateCertificateRequest` accepts `*mldsa.PrivateKey`. `SignatureAlgorithm(crt)` derives the CSR's signature algorithm from the key: `size` maps to `x509.MLDSA44`, `x509.MLDSA65` or `x509.MLDSA87`. This is internal only; there's no API value for it.
- CSR verification (`certificatetemplate.go`): `CheckSignature` works unchanged on Go 1.27.
- `SignCertificate`: gets a `*mldsa.PublicKey` case in the type switch on the signer's public key, and `signatureAlgorithmFromPublicKey` maps it to `x509.MLDSA44/65/87`. As today, the **issuer's** key decides the certificate's signature algorithm, so mixed chains need no special handling. For example:
  - an ML-DSA leaf under a P-256 ECDSA CA is signed with `ECDSA-SHA256` (the hash follows the CA's curve)
  - an ECDSA leaf under an ML-DSA-65 CA is signed with `ML-DSA-65`

- `ca.crt` handling is unchanged.

### Issuers

| Issuer | Behaviour |
|---|---|
| SelfSigned | Supported. Works through `SignCertificate`. |
| CA (and ClusterIssuer) | Supported, with an ML-DSA or classical CA keypair. The Issuer's `Ready` condition shows key-parsing errors (for example the OpenSSL `both` format). |
| Kubernetes CSR signers (`issuers.cert-manager.io/*`, `clusterissuers.cert-manager.io/*`) for SelfSigned/CA | Supported. They share the `pkg/util/pki` code. These signers are themselves behind the `ExperimentalCertificateSigningRequestControllers` gate. |
| ACME, Vault, Venafi/NGTS, external issuers | **Not blocked by cert-manager.** The ML-DSA CSR is sent unchanged and the CA accepts or rejects it. A rejection shows up as a failed CertificateRequest, exactly as it does today for Ed25519 CSRs sent to CAs that don't support Ed25519. Nothing ever re-keys with a classical algorithm. Not tested in v1, and documented as unsupported. |

The SelfSigned and CA issuers and the Kubernetes CSR signers check the `MLDSAPrivateKeys` gate before signing anything that involves an ML-DSA key, whether it's the CSR's key or the issuer's own. Without that check, a Go 1.27 build would sign ML-DSA CSRs with the gate off, as described in [Caveats](#notesconstraintscaveats). Kubernetes CertificateSigningRequests don't go through cert-manager's webhook, and the ACME, Vault and Venafi signers already pass their CSRs to the CA without checking the signature, so for those signers nothing changes.

We chose pass-through over blocking on purpose. It's consistent with how Ed25519 is handled, it leaves private ACME/Vault/external CAs free to add ML-DSA support without a cert-manager release, and blocking wouldn't make anything safer, because the CA rejecting the CSR is already a clear failure.

### Certificate lifecycle

- **Re-issuance triggers** (`internal/controller/certificates/policies/checks.go`): these work through `PrivateKeyMatchesSpec`. Changing the algorithm (for example RSA → MLDSA) or the parameter set (for example 65 → 87) triggers re-issuance. With `rotationPolicy: Never`, the key manager emits the existing `CannotRegenerateKey` warning event and waits for the user, as it does today for any key/spec mismatch.
- `rotationPolicy: Always` / `Never`, renewal, controller restart and reconciling from an existing Secret all work through the paths above, and integration tests will cover them.
- **Feature gate disabled in the controller.** For a Certificate with `algorithm: MLDSA` (created while the gate was on), the trigger controller doesn't start issuance, and emits a Warning event with reason `MLDSAPrivateKeysDisabled` and an explanatory message. As defence in depth, the key manager also refuses to generate ML-DSA keys while the gate is off. The existing Secret is **left alone**: no deletion, so workloads keep running until the certificate expires. Whether to also show this as a condition is an open question. The trigger controller owns the `Issuing` condition, so a value written by anything else would flap; a new condition type might be clearer.
- **Key generation errors** are logged by the key manager, which retries with backoff, but it doesn't record an event or condition today. The implementation should add a Warning event so that users can see why an ML-DSA Certificate isn't being issued.

### Ingress and Gateway annotations

`pkg/controller/certificate-shim/helper.go` accepts `cert-manager.io/private-key-algorithm: MLDSA`, and `cert-manager.io/private-key-size: 44|65|87`. The shim checks sizes per algorithm itself (it doesn't call the webhook validation code), so it needs its own ML-DSA size check, plus a check of the `MLDSAPrivateKeys` gate. Invalid values, or `MLDSA` with the gate off, give the existing `BadConfig` warning event on the Ingress or Gateway, and no Certificate is created or updated.

### Additional output formats and keystores

- `CombinedPEM` and `DER` output formats work unchanged.
- **PKCS#12:** `software.sslmate.com/src/go-pkcs12` (v0.7.3) uses `x509.MarshalPKCS8PrivateKey` for every profile, including the default `LegacyRC2`, so it encodes ML-DSA keys correctly. In the prototype, OpenSSL 3.6 read back a `Modern2026` keystore fine.
- **JKS:** `keystore-go` stores the PKCS#8 DER from `x509.MarshalPKCS8PrivateKey`, so encoding succeeds. Whether a JVM can load it depends on the Java version (JDK 24+ has ML-DSA via JEP 497). We'll check this in the interop spike.
- Both keystores are **allowed** in v1, with a documented note that consumer support varies. We won't block something that works.

### Size limits

`internal/pem` limits are derived from `maxCACertificatePEMSize = 6500` bytes. An ML-DSA-65 root (7525 bytes) or ML-DSA-87 root (10178 bytes) goes over that *estimate*, but the constant isn't enforced on its own. What's actually enforced is:

- a single certificate: 36.5 KB (in practice this limit applies to CSRs, which are decoded with it)
- a chain: 95 KB
- a bundle: 330 KB

All realistic ML-DSA chains fit (sizes vary a little with the subject and extensions); a full ML-DSA-87 root + intermediate + leaf is about 30 KB. A pathological 10-certificate ML-DSA-87 chain (about 100 KB) would go over the chain limit. For v1 we will **not** change the limits. We'll update the comment to describe ML-DSA sizes and add a unit test proving that a 4-deep ML-DSA-87 chain parses. Operators can still raise the limits through the existing configuration (`NewSizeLimitsFromConfig`).

### Test Plan

**Unit** (`pkg/util/pki`, `internal/pem`, validation, `certificate-shim`):
- Generate, encode, parse, CSR, sign and verify round trips for ML-DSA-44/65/87.
- Mixed chains in both directions. Root → intermediate → leaf verification with `x509.Verify`.
- Negative cases:
  - malformed or truncated PEM
  - a CSR with a bad signature
  - unsupported sizes
  - any `signatureAlgorithm` set together with `algorithm: MLDSA`
  - OpenSSL `both`-format and expanded-only keys, which must give Go's error messages
- Validation tests with the gate on and off, including the update-ratcheting case, status updates, and CertificateRequests with ML-DSA CSRs.
- `PrivateKeyMatchesSpec` / `checks.go` for algorithm changes and 65 → 87.
- `PublicKeysEqual` / `PublicKeyForPrivateKey` with ML-DSA keys.
- "An ML-DSA certificate, CSR or key never causes a panic" cases for every `pkg/util/pki` function that inspects keys.
- Keep #8527's PEM round-trip test.

**Integration** (`test/integration`): issuing and renewal with `rotationPolicy` Never and Always, controller restart, the gate disabled while an ML-DSA Certificate exists, PKCS#12/JKS/CombinedPEM output.

**E2E** (`test/e2e`):
- Add `featureset.MLDSAFeatureSet`.
- Add ML-DSA cases to the Certificates and CertificateSigningRequests conformance suites. Mark the feature unsupported everywhere except SelfSigned and CA: for Certificates that's the `acme`, `external`, `vault`, `venafi` (TPP), `venaficloud` and `venafingts` suites, and for CertificateSigningRequests the `acme`, `vault` and `venafi` suites.
- SelfSigned/CA chain scenarios.
- Enable the gate in the e2e cluster.

**Interop** (not in CI, tracked in a follow-up issue): a compatibility matrix for ingress-nginx, Envoy/Istio, OpenSSL, JVM and Go TLS. The prototype already confirmed that Go 1.27 ↔ Go 1.27 and Go server ↔ OpenSSL 3.6 `s_client` TLS 1.3 handshakes succeed with ML-DSA certificates.

### Graduation Criteria

We aim for beta in v1.23 and GA in v1.24, but these are targets, not commitments. There are no fixed waiting periods: the signal to move on is that maintainers are happy with ML-DSA in cert-manager.

**Alpha (v1.22)**, gate `MLDSAPrivateKeys` defaults to off:
- Implemented for SelfSigned, CA and the Kubernetes CSR signers. Unit, integration and e2e tests pass.
- Docs published, including the canary migration guide and known limitations.

**Beta (target v1.23)**, gate defaults to on:
- Maintainers are happy with ML-DSA in cert-manager, and no known ML-DSA-specific bugs are open.

**GA (target v1.24)**, gate locked on and later removed:
- Maintainers are happy for the feature to be permanently enabled.

### Upgrade / Downgrade Strategy

- **Upgrade:** no effect until a user sets `algorithm: MLDSA` (and, while the gate is alpha, enables the gate).
- **Downgrade to a version without ML-DSA support:** users must switch every ML-DSA Certificate to a classical algorithm, and wait for it to be re-issued, **before** downgrading (or delete those Certificates). Release notes and docs will say so. If they don't:
  - The older webhook rejects every update to a Certificate with `algorithm: MLDSA`, including the controller's status updates, so those Certificates are stuck. On Kubernetes 1.30+, CRD validation ratcheting means the older CRD enum alone wouldn't block updates that leave the field unchanged; the webhook does.
  - An older controller without the `PrivateKeyMatchesSpec` fix [described above](#key-generation-encoding-and-parsing) panics on these Certificates, and keeps crash-looping, which stops renewals for **every** Certificate. This is why users must convert or delete ML-DSA Certificates before downgrading.
  - Workloads keep running on the existing Secrets until the certificates expire.
- **Disabling the gate:** see [Certificate lifecycle](#certificate-lifecycle). Existing Secrets are kept, renewal stops, and a Warning event explains why.

### Supported Versions

- Kubernetes: every version supported by the cert-manager release. Nothing here depends on Kubernetes.
- Go: cert-manager is built with Go 1.27.1+, and its `go.mod` files require Go 1.27, including for library consumers.

## Production Readiness

### How can this feature be enabled / disabled for an existing cert-manager installation?

While the gate is alpha, set `--feature-gates=MLDSAPrivateKeys=true` on both the controller and the webhook (`featureGates` and `webhook.featureGates` in Helm). Once it's beta, it's on by default and can be turned off with `MLDSAPrivateKeys=false`. Turning it off is safe. Existing ML-DSA Secrets are kept, no new ML-DSA keys are issued, affected Certificates get a `MLDSAPrivateKeysDisabled` Warning event, and the webhook still lets users edit or delete those Certificates. Tests cover both gate states.

### Does this feature depend on any specific services running in the cluster?

No. Whether workloads can *use* the issued certificates depends on the consumer (see Caveats).

### Will enabling / using this feature result in new API calls (i.e to Kubernetes apiserver or external services)?

No. Issuance follows the existing flow.

### Will enabling / using this feature result in increasing size or count of the existing API objects?

There are no new objects, but objects using ML-DSA are bigger:
- `tls.crt` (leaf + intermediate) is about 11–20 KB, and `tls.key` is smaller than RSA (128 bytes).
- A CertificateRequest stores the CSR, the certificate and the CA as base64 of PEM, which adds about a third. An ML-DSA-87 CertificateRequest is roughly 40–55 KB in total. `revisionHistoryLimit` bounds how many are kept per Certificate.

The CRD schema grows by 1 enum value.

### Will enabling / using this feature result in significant increase of resource usage? (CPU, RAM...)

No. ML-DSA key generation and signing take around a millisecond or less on typical hardware, much less than RSA-2048 key generation. The slightly bigger cached Secrets add negligible memory.

## Drawbacks

- Users can now create Secrets that some of their consumers can't load. This is mitigated by the gate, the opt-in model and the documentation.
- More code paths to maintain.
- Projects that import cert-manager as a library must move to Go 1.27.
- Reusing `size` for parameter sets is slightly overloaded, though ECDSA set the precedent.

## Alternatives

1. **Start new PRs instead of finishing #8527.** #8527 was originally based on `cloudflare/circl` and hand-built ASN.1, but it now uses the standard library, so finishing it is less work and keeps its author involved. See [Relationship to #8527](#relationship-to-8527).
2. **Separate enum values `MLDSA44`/`MLDSA65`/`MLDSA87` for `privateKey.algorithm`.** Simpler validation, but `size` would be ignored (as for Ed25519) and there would be three algorithm values for one x509 public key algorithm. We chose `algorithm: MLDSA` plus `size` to match how ECDSA works and to keep the algorithm enum short. Maintainers have said `size` may well make sense; the final decision is theirs.
3. **A dedicated `parameterSet` field.** Adds API surface for very little gain over `size`.
4. **Signature algorithm values for ML-DSA.** Either `MLDSA44`/`MLDSA65`/`MLDSA87` to match the `crypto/x509` constants, or a single catch-all `MLDSA`. Rejected: each key allows only one signature algorithm, and the issued certificate's signature depends on the signer, so these values give users nothing to choose and only add a way to get it wrong. `PureEd25519` arguably has the same problem, but it's an existing API value, so this design leaves it alone.
5. **Keep the `go` directive at 1.26, and put the ML-DSA code behind a `go1.27` build tag with a stub.** Library consumers could stay on Go 1.26, but it adds a stub package, a restriction on where `crypto/mldsa` may be used, and extra CI jobs on an older Go version. Rejected, because cert-manager itself comes first and library consumers don't justify that cost.
6. **Block ML-DSA for non-SelfSigned/CA issuers.** Rejected. It's inconsistent with Ed25519, and it would stop private CAs that do support ML-DSA. A CA rejection is already a clear failure.
7. **Default parameter set 65 (NIST category 3).** A reasonable choice for maintainers to consider. We propose 44 for the reasons given in [API](#api).

## Appendix: prototype measurements

Measured on 2026-10-07 with Go 1.27.1 (darwin/arm64) and OpenSSL 3.6.4. The prototype was a throwaway Go module.

| | ML-DSA-44 | ML-DSA-65 | ML-DSA-87 |
|---|---|---|---|
| Public key / signature (bytes) | 1312 / 2420 | 1952 / 3309 | 2592 / 4627 |
| `tls.key` PEM, PKCS#8 seed-only | 128 B | 128 B | 128 B |
| `tls.crt` PEM, leaf + intermediate | 10,956 B | 15,099 B | 20,405 B |
| `ca.crt` PEM, root | 5,454 B | 7,525 B | 10,178 B |
| CSR PEM | 5,275 B | 7,346 B | 9,999 B |
| CSR `CheckSignature`, chain `Verify`, PKCS#8 round trip | ok | ok | ok |
| Go ↔ Go TLS 1.3 handshake | ok | ok | ok |

Other results:
- Go server with an ML-DSA-65 certificate ↔ `openssl s_client`: TLS 1.3, peer signature `mldsa65`, group `X25519MLKEM768`, verify OK.
- OpenSSL reads Go-generated ML-DSA certificates and keys, and `openssl verify` passes.
- Go reads OpenSSL keys as follows: `seed-only` ✅, `priv-only` ❌ (not supported), `seed-priv` (OpenSSL's default) ❌ with an error suggesting the conversion command.
- PKCS#12 (`go-pkcs12` `Modern2026`) encodes and decodes an ML-DSA key, and `openssl pkcs12` reads it. JKS (`keystore-go`) encodes it; JVM loading is untested.

## Appendix: answers to the questions raised in #8929

1. ***Is `algorithm: MLDSA` with `size: 44|65|87` consistent with the desired long-term API, or should parameter sets use a dedicated field?*** We think `size` is the right place. This design proposes `algorithm: MLDSA` with `size` (see [API](#api) and [Alternatives](#alternatives) 2–3), and maintainers have the final say.
2. ***Feature gate, and CRD behaviour when the gate is disabled?*** Gate `MLDSAPrivateKeys` on both the controller and the webhook: alpha in v1.22, with beta in v1.23 and GA in v1.24 as targets. The CRD enum always includes `MLDSA`, and the webhook rejects new uses while the gate is off but allows existing values to stay unchanged on update. With the gate off, the webhook also rejects CertificateRequests with ML-DSA CSRs, and the SelfSigned and CA issuers won't sign ML-DSA certificates.
3. ***Rework #8527 after the Go upgrade, or a new standard-library PR coordinated with its author?*** Rework #8527. It already uses the standard library and moves to Go 1.27. The changes it still needs are listed in [Relationship to #8527](#relationship-to-8527). If maintainers prefer smaller PRs (API → PKI → issuers → controller → shim → e2e), we'll split it with the author credited as co-author.
4. ***Consumer interoperability tests in-tree, or stop at valid X.509 output plus a documented canary process?*** In-tree tests stop at valid X.509/Secret output plus Go TLS handshakes. Consumer compatibility goes in a documented matrix (a follow-up issue) and the canary guide, not in CI.
